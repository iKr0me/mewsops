# Mobile integration, round 1

The standalone `mobile/src/services/mewsApi.ts` targets the HTTP implementation at main `fc7b0e7`, checked against `src/app.ts`, domain services and `docs/api-contract.md` on 8 November 2026. The local backend checkout was behind; the frontend checkout included that main API commit. It is not wired to UI. The server remains authoritative for validation, scope and roles. Endpoint types describe the current contract at compile time; only the JSON envelope is checked at runtime, so validate full payloads before trusting an independently deployed or changed server.

Create the client with an explicitly supplied HTTP(S) **origin**, e.g. `createMewsApi({ baseURL: origin })`. No server address, token, login, demo session or role is configured by the client. Credentials default to `same-origin`; a caller may opt into browser `include` for a supported authenticated cross-origin server or inject a fetch implementation for a future verified authentication transport. Neither establishes authentication. Do not put secrets in the app or URLs. Abort signals are supported; a network error or aborted write does not prove the server did not persist it. Preserve the same `clientRequestId` and identical payload when recovering a report receipt; use a new key for changed payload. On 409, refresh before deciding again. No automatic retries are made.

## Gaps before real integration

- The provided startup binds `127.0.0.1:3000`, and its demo session endpoint only accepts loopback clients and loopback Host. A physical phone cannot reach that service at its own localhost or use the loopback-only demo login. The injected `verifiedSubject` server hook is not a login implementation; real verified sessions and a secure reachable server remain team-owned work. Never expose demo persona switching publicly. Native cookie persistence, refresh, logout and secure session transport are unproven and require an agreed auth contract and device tests.
- The server implements no CORS response/preflight support and rejects cross-origin POSTs. Merely setting `credentials: 'include'` does not enable a separate web origin. A same-origin deployment or a reviewed server-side CORS/CSRF and session design is required. HTTPS, private media authorization and a durable backend must be addressed before real use.
- Media upload takes raw JPEG/PNG bytes, not multipart; `uploadMedia` accepts a Blob. Web can supply a browser Blob; native image selection, URI-to-bytes conversion, permissions, memory limits, upload progress and reliable binary behavior have not been implemented or tested. Private media is fetched as a Blob; native display and lifecycle management remain unverified. Do not expose private media as public URLs.
- The API has no HTTP route to record a feeding visit, correct an observation link, acknowledge/assign alerts, or create a production session. A photo or sighting is not feeding evidence. Report processing is staff-only and separate from submission. Identity decisions require current versions and server confirmation. Fixture inference is not a live model.
- Do not treat a success type assertion as runtime schema validation. No end-to-end browser or native connection, actual user authentication, device media transfer, offline persistence or deployment was verified in this lane.
